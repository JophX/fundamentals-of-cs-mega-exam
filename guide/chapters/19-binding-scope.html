19. Names, scope and types PL

In Part I we saw how an interpreter turns text into a tree. Now the tree has to run — and the first thing it runs into is names. Your code says x. Which x? Where does its value live? When is it created, when does it die, and what is it allowed to hold? Every language has to answer these questions, and the answers are what the “explain” questions on your exam are about. Once you see them as design decisions — choices a language designer made, each with a price — they stop being a list of terms and start making sense.

The shape of a full-points “explain” answer

(1) a precise definition, (2) how it works, (3) a tiny example, (4) an advantage and a disadvantage, (5) how it differs from the neighbouring concept. Five sentences like that almost always get full points. We’ll use that shape throughout Part IV.

19.2 What a variable really is

In an imperative language, a variable is a named box in memory. It has six attributes, and it’s worth being able to list them: name, address (where the box is), value (what’s in it), type (what may go in it), lifetime (when the box exists) and scope (where in the code the name can be used).

A binding is any association between a name and one of these things, and binding time is when it happens: some are fixed when the language is designed (* means multiply), some at compile time (the type of int x in Java), and some only at run time (the value of x, or the address of a local variable). Binding that happens before the program runs and never changes is static; binding that happens or changes while it runs is dynamic. That one pair of words — static/dynamic — comes back again and again in this Part.

Where do the boxes live? A running program’s memory looks like this:

digraph{node[shape=record fontname="Helvetica" width=3.5]; m[label="{stack: one activation record per active call (return address, parameters, locals) — grows ↓|free memory|heap: objects made with new / malloc — grows ↑|global and static data, constants|program code}"];}
  • Static variables (globals) exist for the whole run.
  • Stack-dynamic variables (locals) are created when a function is called and destroyed when it returns. This is what makes recursion possible: each call gets its own fresh set.
  • Heap-dynamic variables are created explicitly (new) and live until freed or garbage-collected.

19.3 Two meanings of “=” — the functional twist

Here’s a question that appeared on the exam: in both Java and Haskell you can write a = b + 4. Why do we call it assignment in one and naming a value in the other? Answer it with the box picture:

Exam (6 p): variables in imperative vs functional languages

In an imperative language a variable is an abstraction of a memory cell. a = b + 4 computes b + 4 and stores it in the cell called a, overwriting what was there. Later the cell can be changed again (a = a + 1), so the meaning of a depends on when you look: the program has state, and assignment is a side effect.

In a pure functional language there are no cells to change. a = b + 4 is a definition: it binds the name a to the value of b + 4, like “let a = b + 4” in mathematics, and that can never change within its scope. (a = a + 1 would be a circular definition, not an update.) Because a name always means the same value, you can replace it by its value anywhere — referential transparency — which makes programs easier to reason about, test and run in parallel. Repetition is done by recursion rather than by updating loop variables. In short: a changeable storage location versus a permanent name for a value.

19.4 Scope: which x is it?

Suppose there are two variables called x — a global one, and a local one inside some function. A function that mentions x without declaring it: which one does it get? There are two possible rules.

  • Static (lexical) scope: look at the program text. The x is the one declared in the nearest block that surrounds the function where it is written. You can answer by reading the code — no need to run it.
  • Dynamic scope: look at the calls at run time. The x is the most recent one created by whoever called you (or their caller, and so on).

In Python, f is written at the top level, so its x is the global one: 1. In bash, f was

Almost every modern language uses static scope, and now you can see why: with dynamic scope, what a function does depends on who
called it, so you can’t understand a function by reading it. Static scope is readable and can be checked by the compiler. Dynamic
scope is flexible but confusing.


Don’t mix up scope (where in the text a name is visible) with lifetime (when the box exists in memory). A C
static local variable has local scope but lives for the whole program.



19.5 Types: what may go in the box


A type system is the set of rules saying which values and operations go together — you can add two numbers, but what does
adding a number to a list mean? Type checking enforces those rules. The big design choice is when:

Other words you should know: strong typing means type errors are always caught (Haskell); weak means some slip through
(C with casts). Type inference means the compiler works out the types itself — Haskell can do this for almost everything.
Coercion is automatic conversion, like Java turning 1 + 2.5 into 1.0 + 2.5.


A Python function def example(a, b): return a + b happily works on numbers, strings and lists. That’s dynamic typing
together with an overloaded + — sometimes called “duck typing”: if it can be added, add it.
