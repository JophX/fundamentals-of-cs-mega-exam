20. Control structures and subprograms PL

20.1 Control structures (lecture 10)

An imperative language is mostly var = expr;. To be Turing complete it needs two more things: conditions (simplest: if) and jumps (simplest and most powerful: goto). Structured programming replaces goto with readable forms:

  • Selection: nested if-then-else (always use blocks — the dangling-else problem), elif; multi-way switch/case (with or without break/fall-through, default case); pattern matching (Haskell, ML).
  • Logical loops: while (e) … (pre-test), do … while (e) (post-test, runs at least once); control with break (leave the loop) and continue (skip to the next iteration).
  • Counter loops and iterators: for x in fruit iterates over a collection (list, tree…) instead of an index — simpler and more flexible.
  • Guarded commands (Dijkstra): if g1 -> s1 [] g2 -> s2 fi picks any true guard (nondeterministically; error if none). do … od repeats until no guard is true. The lecture’s example sorts four variables by swapping any out-of-order neighbours until none is — the order of swaps doesn’t matter. Used to reason about correctness and concurrency.

20.2 Subprograms

  • Process abstraction: procedures do something (change state), functions return a value, methods are procedures/functions belonging to objects/classes.
  • A header defines name, parameters and result type.
  • Design issues (slide): when/how are parameter types checked? Nested subprograms allowed? Subprograms as parameters? Overloading (same name, different parameter types)? Generic subprograms (one definition for many types)? Side effects allowed? What can be returned, and how many values?
  • Co-routines: not master/slave — two routines pass control back and forth, each resuming where it left off (several entry points). Used for quasi-concurrency, generators, pipelines.
