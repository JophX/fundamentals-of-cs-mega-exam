22. Interpreters: lexer, parser, executor PL

This is the chapter where the whole story comes together. Everything from Part I — finite automata, regular expressions, grammars, stacks, parse trees — and everything from Part IV — names, scopes, environments, call stacks — are the parts of one machine: the thing that runs your code.

The idea in plain words

Your program is, to the computer, just a long string of characters: x = 2 + 3 * 4;. To run it, the language implementation works like reading a sentence in a foreign language:

  1. Lexer (scanner) — find the words. Group characters into meaningful chunks and label them: x is an identifier, = is an assignment sign, 2 is a number… Throw away spaces and comments.
  2. Parser — find the grammar/structure of the sentence. Check that the words are in a legal order and build a tree that shows what belongs to what: the 3 * 4 is done first and then added to 2.
  3. Executor (interpreter) — do what the sentence says. Walk the tree, compute the values, store 14 in x.

22.1 Lexer (scanner)

Inputthe source code as a string / stream of characters
Outputa list (sequence) of tokens
TaskGroup characters into lexemes (the smallest meaningful pieces: while, x1, 3.14, >=) and classify each one as a token. A token typically stores: its type (IDENTIFIER, NUMBER, PLUS, keyword WHILE…), the lexeme text, the literal value (e.g. the number 3.14) and the line number (for error messages). It discards whitespace and comments, recognises keywords, and reports lexical errors (an illegal character like #, an unterminated string).
TheoryTokens are described by regular expressions (identifier = [a-zA-Z_][a-zA-Z0-9_]*), so the lexer is a finite automaton. It follows the “longest match” rule: >= is one token, not > then =; whilex is an identifier, not the keyword while.
Data structuresa character buffer/string with position pointers (start of the current lexeme, current character); a hash table of keywords (reserved words); the output list/array of tokens; sometimes it inserts identifiers in a symbol table.

22.2 Parser

Inputthe list of tokens from the lexer
Outputa syntax tree — usually an abstract syntax tree (AST) — or syntax errors
TaskCheck that the token sequence follows the grammar of the language (the syntax), and build a tree that shows the structure of the program: which operands belong to which operator, which statements are inside which loop/block/function. Precedence and associativity are decided here: from 2 + 3 * 4 the parser builds Add(2, Mul(3, 4)). It reports syntax errors with a position (“expected ‘)’ at line 7”) and tries to recover (skip to the next statement) to report more than one error.
TheoryThe syntax is described by a context-free grammar (BNF), because programs have nesting (parentheses, blocks inside blocks) that regular expressions cannot describe. A parser is in effect a pushdown automaton: it needs a stack. Common techniques: recursive descent (top-down: one function per grammar rule; the call stack is the stack), LL, and LR/LALR (bottom-up, e.g. generated by yacc/bison). An ambiguous grammar is a problem for the parser, since one program would get two trees (two meanings).
Data structuresthe token list with an index to the current token (lookahead); a stack (explicit in LR parsers, or the recursion call stack in recursive descent); the output tree (nodes = operators, statements; leaves = literals, identifiers); often a parse table (LL/LR).

22.3 Between parser and executor: static (semantic) analysis

Things the grammar cannot check: Is this variable declared? Which declaration does this name refer to (scope resolution)? Do the types fit (in statically typed languages)? This pass walks the tree and uses a symbol table (hash maps, one per scope, stacked/chained for nested scopes). It may annotate the tree with the results.

22.4 Executor (the interpreting part)

Inputthe (annotated) syntax tree
Outputthe program’s behaviour: values, output, side effects; or runtime errors
TaskWalks the tree recursively: to evaluate an Add node, evaluate both children then add (post-order). Executes statements in order, handles control flow (if, loops, calls, return, exceptions), looks up and updates variables, calls functions, reports runtime errors (division by zero, type errors in dynamically typed languages, undefined variable).
Data structuresthe AST; an environment = mapping from names to values, implemented as a hash table, with one table per scope linked to its enclosing scope (a chain of hash tables); a call stack of activation records (parameters, local variables, return address) for function calls; a heap for objects, closures, strings. A bytecode interpreter instead uses an array of instructions and a value stack.
Interpreter vs compiler (often asked together)

A compiler translates the whole program to another language (e.g. machine code) before it runs; the lexer and parser are the same, but the last stage generates code instead of executing. An interpreter executes the program directly from its tree (or bytecode). Hybrid: compile to bytecode, then interpret it in a virtual machine (Java, Python), possibly with a JIT compiler. Interpreter: easier, portable, good error messages, slower. Compiler: faster execution, errors found before running, less flexible.

22.6 Precedence and associativity (asked on both 2023 exams, 6 p)


Model answer: “Briefly describe precedence and associativity. How are they related in the context of programming languages?”

Precedence decides which of two different operators binds tighter when there are no parentheses.
* has higher precedence than +, so 2 + 3 * 4 means 2 + (3 * 4) = 14,
not (2 + 3) * 4 = 20.


Associativity decides how operators of the same precedence level are grouped. - is
left-associative: 10 - 4 - 3 = (10 - 4) - 3 = 3, not 10 - (4 - 3) = 9.
Exponentiation and assignment are usually right-associative: 2 ^ 3 ^ 2 = 2 ^ (3 ^ 2) = 512;
a = b = 0 = a = (b = 0). Some operators are non-associative (a < b < c is an error
in some languages).


Relation: both are rules for resolving the ambiguity of expressions written without parentheses, i.e. for
deciding the shape of the syntax tree. Precedence is applied first (between levels); associativity is only needed when
operators have the same precedence. In a grammar they are encoded structurally: one nonterminal per precedence level
(expr → expr + term | term, term → term * factor | factor, factor → num | ( expr )) —
lower levels are deeper in the tree, so they bind tighter; left recursion (expr → expr + term) gives
left associativity, right recursion (pow → base ^ pow) gives right associativity. They matter because they
change the result (10-4-3) and, with side effects, behaviour. Parentheses always override both.





Model answer: “Describe as much as the space permits the role of a parser in a program”

The parser is the second phase of an interpreter/compiler, after the lexer. Its input is the sequence of tokens
produced by the lexer (e.g. ID(x) ASSIGN NUM(2) PLUS NUM(3) STAR NUM(4)). Its job is syntax
analysis: it checks that the token sequence can be derived from the language’s context-free grammar, and it
builds a syntax tree (usually an abstract syntax tree) that represents the hierarchical structure of the program —
which statements are inside which blocks, and which operands belong to which operators. When building the tree the
parser applies the language’s precedence and associativity rules, so 2+3*4 becomes
+(2, *(3,4)). If the tokens do not fit the grammar it reports a syntax error with its location and
tries to recover to find further errors. The tree is the input to the later phases: semantic analysis (scopes, type
checking, with a symbol table) and then execution (interpreter) or code generation (compiler). A common technique is
recursive descent, where each grammar rule becomes a function and the recursion stack plays the role of the
pushdown automaton’s stack; other parsers are table-driven (LL, LR). Data structures used: the token list with a
current position, a stack (explicit or the call stack), and the tree it outputs.





Model answer: “An interpreter consists of a scanner/lexer, a parser and an executing part. What are their tasks and what data structures do they use?” (8 p)

Lexer: reads the source text character by character and groups characters into lexemes, which it classifies as
tokens (type, lexeme, value, line). Skips whitespace and comments, distinguishes keywords from identifiers, reports lexical
errors. Works like a finite automaton defined by regular expressions. Data structures: input string/buffer with
position pointers, keyword hash table, output list of tokens.


Parser: takes the token list and checks it against the context-free grammar of the language; builds a syntax tree
(AST) that captures structure, precedence and associativity; reports syntax errors. Recursive descent or table-driven (LL/LR).
Data structures: token list + index, a stack (call stack in recursive descent), the tree (and possibly a symbol table).


Executor: traverses the tree and carries out the computation: evaluates expressions recursively, executes statements,
handles control flow and function calls, looks up/updates variables, reports runtime errors. Data structures: the AST,
environments (hash tables mapping names to values, chained for nested scopes), a call stack of activation records (parameters,
locals, return address), and a heap for dynamically allocated data.
