23. Doing several things at once — and when things go wrong PL

23.1 Concurrency

Your phone plays music while you type a message and an app downloads in the background. Several things are happening at once. Sometimes truly at once (several processor cores), sometimes only apparently (one core switching between tasks very quickly). Either way, we call it concurrency.

Why bother? Because the world is concurrent (a program that models it naturally is too), because it keeps programs responsive (the interface keeps reacting while the heavy work happens in another thread), and because modern machines have many cores to use.

The problem: sharing

If concurrent tasks never talked to each other, there’d be no problem. The trouble starts when they share data. Picture two threads each doing count = count + 1, which is really three steps: read, add, write.

Thread AThread Bcount
reads 55

Two increments, but count went up by one. The result depends on timing — a race condition. It might work a thousand times and fail on the thousand-and-first. So languages need ways to synchronise: make sure only one task at a time is in a critical section (mutual exclusion), and let tasks wait for each other (cooperation).

The four tools

ToolHow it worksTrade-off
SemaphoreA counter with two atomic operations. wait: if the counter is above zero, decrease it and go on; otherwise block. signal: if someone is blocked, wake one; otherwise increase the counter.Tiny and simple — but the programmer must get every wait/signal right. One mistake: deadlock or a race.
MonitorA language construct that wraps shared data with its operations, and guarantees only one thread is inside at a time (like Java’s synchronized).Much safer; but can lock more than necessary, reducing parallelism.
Message passingTasks don’t share memory at all; they send each other messages, like letters (synchronously or not).Easy to understand, works across machines; costs speed and resources.
Transactional memoryMark a block as a transaction: it either completes entirely, or is rolled back, as in a database.Easy for the programmer; overhead, not available everywhere.

Two failure words to know: deadlock — A holds X and waits for Y, B holds Y and waits for X; both wait forever. Starvation — a task that never gets its turn.

23.2 Exceptions: when things go wrong

Things go wrong in three flavours: the truly unexpected (disk failure), the unexpected-but-possible (division by zero, overflow), and the expected (end of file). You could handle all of them by checking return values after every call — but code full of if (error) … is hard to read. So modern languages use try–catch:

  • the normal code is written cleanly inside try;
  • when an error occurs, an exception is raised (thrown) and normal execution stops;
  • if the current function has no matching catch, the exception propagates up the chain of callers until one does — so errors can be handled at whichever level knows what to do about them;
  • finally runs cleanup code no matter what.

Designers have to decide: can exceptions carry information? how is the right handler chosen when there are several? where should handling happen? what happens if nobody catches it?

23.3 Events

An event is a cousin of an exception that isn’t about errors: a button is clicked, a key is pressed, a timer fires, and a handler you registered earlier is called. Instead of the program deciding when to look for input, the input calls the program. That’s how every graphical interface works.
