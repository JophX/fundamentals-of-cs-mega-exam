23. Concurrency, exceptions and events PL

23.1 Concurrency

Intuition

Several things happen at the same time. Truly concurrent = several physical processors. Logically concurrent = one processor switching between tasks (simulating several). Levels: machine instructions, expressions/statements, subprograms, whole programs. Our focus: many different things happening at once and communicating (not squeezing out performance, HPC).

Why: reality is parallel (modelling); better responsiveness (a GUI thread keeps reacting while work goes on); using several cores/processors/machines.

The problem: concurrent tasks must share data and resources. If one thread changes data another is using, the result depends on timing — a race condition. Example: two threads do count = count + 1 (read, add, write); if both read 5 before either writes, both write 6 and one increment is lost. So we need synchronisation: mutual exclusion (only one at a time in a critical section) and cooperation (wait until another task has produced something).

Deadlock: tasks wait for each other forever (A holds X, wants Y; B holds Y, wants X). Starvation: a task never gets its turn.

23.2 Exception handling

Kinds of error: truly unexpected (memory/disk failure), unexpected but possible (overflow, division by zero), expected (end of file). Hardware or software detects it and raises an exception: try to recover, or terminate.

You could check return values and flags everywhere, but the code becomes messy. Modern languages use try–catch(–finally): clearer code, you think explicitly about which errors can occur, and you can handle an error at the level that knows what to do — an exception not caught locally propagates up the call chain to the nearest matching handler.

Design questions (slide): how is an exception raised; can it carry parameters/information; can it be handled at different levels and how does propagation work; where should errors be handled; how is the right handler chosen among several; is there finally (cleanup that always runs)?

23.3 Events

An event is not an error but a way of programming: something happens (a click, a key, a timer) and a registered handler is called. Events resemble exceptions (both come from hardware signals and interrupt vectors) and messages between threads. Java’s listener model is typical.
