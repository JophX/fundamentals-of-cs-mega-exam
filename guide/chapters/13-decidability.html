13. What no machine can do FCS

You’d think a machine powerful enough to run any program could answer any well-defined yes/no question. This chapter shows that’s false — and not for some exotic question, but for a very practical one: “will this program ever stop?”

13.1 Two kinds of “solving”

A Turing machine that answers questions can behave in two ways, and the difference is everything:

  • A decider always halts: “yes” or “no”, every time. A language with a decider is recursive (= decidable).
  • A recognizer halts with “yes” on every yes-instance, but on a no-instance it may say “no” — or run forever. A language with a recognizer is recursively enumerable (RE).
Why the difference matters

If a recognizer has been running for an hour, you don’t know whether the answer is “no” or “not yet”. A decider never leaves you hanging.

One neat consequence: if a language and its complement are both RE, the language is decidable. Run both recognizers side by side, one step each; one of them must eventually say yes — and then you know the answer.

True/false traps

“It can be correct to say that a Turing machine M is decidable” — false: languages or problems are decidable; a machine is a decider or not. “The set of (encoded) Turing machines is RE” — true: a machine can check whether a string is a valid encoding.

13.2 There are more problems than programs

Before the halting problem, a simpler shock. Machines are finite descriptions — strings — so we can list them all: machine 1, machine 2, machine 3… (countably many). But how many languages are there? Let’s try to list them too and see what goes wrong:

Cantor’s diagonal trick

Suppose someone claims they’ve listed every language: \(L_1, L_2, L_3,\dots\). List all strings too: \(w_1,w_2,w_3,\dots\). Now build a new language \(D\) by going down the diagonal and doing the opposite: put \(w_i\) in \(D\) exactly when \(w_i\) is not in \(L_i\).

Is \(D\) on the list? It can’t be \(L_1\) — they disagree about \(w_1\). It can’t be \(L_2\) — they disagree about \(w_2\). It can’t be any \(L_i\). So the list was incomplete. No list of languages can ever be complete: there are uncountably many.

So there are more languages than machines — most languages have no machine at all. That’s abstract, though. Let’s find a real one.

13.3 The halting problem

Question: given a machine \(M\) and an input \(w\), does \(M\) halt on \(w\)?

It is RE: just run \(M\) on \(w\) (with the universal machine), and say yes if it halts. But is it decidable? Suppose it were — suppose there is a perfect machine \(H\) that always correctly answers “does \(M\) halt on \(w\)?”. Watch what we can build with it:

The proof — a machine that contradicts itself

Build a troublemaker \(D\). On input \(\langle M\rangle\) (a machine’s description), \(D\) asks \(H\): “does \(M\) halt when given its own description?” Then \(D\) does the opposite: if \(H\) says “halts”, \(D\) loops forever; if \(H\) says “loops”, \(D\) halts.

Now feed \(D\) its own description. Does \(D\) halt on \(\langle D\rangle\)?

  • If it halts, then \(H\) said “\(D\) loops” — so \(H\) was wrong.
  • If it loops, then \(H\) said “\(D\) halts” — wrong again.

Either way \(H\) is wrong. So a perfect \(H\) cannot exist: the halting problem is undecidable. (And since it is RE but not decidable, its complement is not even RE.)

Notice it’s the diagonal trick again: \(D\) is built to disagree with every machine on that machine’s own description.

13.4 Reductions: spreading the impossibility

Once one problem is known to be impossible, we can show others are impossible without starting from scratch. The argument goes: “if I could solve your problem, I could use it to solve the halting problem — and that’s impossible, so I can’t solve yours either.”

Recipe: proving problem B undecidable
  1. Assume B has a decider.
  2. Take any halting question “does \(M\) halt on \(w\)?”. Show how to transform it (by an algorithm that always finishes) into a B-question with the same answer.
  3. Then B’s decider would decide halting. Contradiction.

Direction matters: you transform the known impossible problem into the new one.

Example: “does \(M\) ever enter state \(q\) on input \(w\)?” Given \(M, w\), build \(M'\): a copy of \(M\) with one extra state \(q_{new}\), and wherever \(M\) would halt, \(M'\) instead goes to \(q_{new}\). Then \(M'\) enters \(q_{new}\) ⇔ \(M\) halts. So a solver for state-entry would solve halting — impossible.

Example: “does \(M\) halt when started on a blank tape?” Given \(M, w\), build \(M_w\): it first writes \(w\) on the tape, then behaves like \(M\). \(M_w\) halts on blank ⇔ \(M\) halts on \(w\).

In fact almost every interesting question about what programs do — “is its language empty?”, “finite?”, “regular?” — is undecidable (Rice’s theorem). This is why no compiler can perfectly detect all infinite loops.

Where we’re going next. Among the problems we can solve, some take a blink and some would take longer than the age of the universe. Measuring that difference is complexity theory.
