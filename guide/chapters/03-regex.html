3. Describing patterns: regular expressions BOTH

A machine checks strings. But often you just want to describe them: “an identifier is a letter followed by letters or digits.” For that we use a tiny language of patterns with only three operations — and it’s worth pausing on how little that is:

  • or — \(a+b\): either an a or a b (the FCS course writes “or” as \(+\));
  • then — \(ab\): an a followed by a b;
  • repeat — \(a^*\): zero or more a’s.

Plus the building blocks: single letters, \(\lambda\) (the empty string) and \(\emptyset\) (nothing). That’s the whole language. Everything else is combining these.

Definition

\(\emptyset\), \(\lambda\) and each letter \(a\) are regular expressions. If \(r_1, r_2\) are, so are \(r_1+r_2\) (union), \(r_1r_2\) (concatenation), \(r_1^*\) (star) and \((r_1)\). Nothing else is.

“+” means two different things in your two courses

In the FCS course, \(a+b\) means “a or b”. In programming (Python, Java, grep), “or” is a|b and a+ means “one or more a’s”. Same symbol, different meaning. On the PL exam, say which notation you use.

3.1 Reading a regex — the order matters

Just like in maths, where \(2+3\times4\) means \(2+(3\times4)\), regular expressions have a precedence order: star binds tightest, then “then”, then “or”.

You writeIt meansNot
\(ab^*\)\(a(b^*)\) — \(a, ab, abb, \dots\)\((ab)^*\)
\(a+bc\)\(a+(bc)\) — just \(a\) or \(bc\)\((a+b)c\)

Keep this in the back of your mind — it’s the exact same idea as operator precedence in programming languages (Chapter 8).

Now read some patterns. The trick is to translate them into a sentence:

RegexSay it in words
\((a+b)^*\)“any string at all”
\((a+b)^*ab\)“anything, then ab” = ends with ab
\((a+b)^*aba(a+b)^*\)“anything, aba, anything” = contains aba
\(a^*ba^*\)exactly one b
\(a^*(\lambda+b)a^*\)at most one b (the \(\lambda+b\) means “a b, or nothing”)
\(((a+b)(a+b))^*\)chunks of two letters = even length
\(a^*(ba^*ba^*)^*\)b’s come in pairs = even number of b’s
\((b+ab)^*(\lambda+a)\)every a is followed by b, except maybe at the very end = no aa

3.2 Writing a regex — a few moves cover almost everything

The moves
  • contains X: \((a+b)^*X(a+b)^*\). starts with X: \(X(a+b)^*\). ends with X: \((a+b)^*X\).
  • exactly two b’s: put them in explicitly, with “anything but b” around them: \(a^*ba^*ba^*\).
  • counting modulo k: a chunk containing exactly k of the letter, repeated: even b’s = \(a^*(ba^*ba^*)^*\).
  • A or B: build each, join with \(+\).

A real exam statement (FCS, true/false): “the strings over \(\{a,b,c\}\) that start with a, or end with c, or have an odd number of b’s form a regular language.” True — each of the three parts is easy to write, and “or” is just \(+\): \[a(a+b+c)^* \;+\; (a+b+c)^*c \;+\; (a+c)^*b(a+c)^*\big(b(a+c)^*b(a+c)^*\big)^*\]

3.3 A few equalities worth knowing

  • \(\lambda r = r\) (gluing on nothing changes nothing) — but \(\emptyset r=\emptyset\) (gluing onto no string gives no string).
  • \(\emptyset^*=\lambda\): repeating nothing zero times still gives the empty string.
  • \((r^*)^*=r^*\), \(\lambda+rr^*=r^*\).
  • \((ab)^*a=a(ba)^*\) — both are \(a, aba, ababa,\dots\).
  • Trap: \((a+b)^*\ne a^*+b^*\). The left allows ab; the right is “only a’s or only b’s”.

3.4 Patterns and machines are the same thing

Here’s the big result of the last two chapters, and it’s genuinely remarkable:

Kleene’s theorem

A language can be described by a regular expression if and only if it can be recognised by a DFA (or NFA). Such languages are called regular.

Why is it true? In one direction, you can build an NFA from a regex piece by piece, the same way you’d evaluate an arithmetic expression from the inside out:

digraph{rankdir=LR; node[shape=circle fontname="Helvetica" width=0.35 label=""]; edge[fontname="Helvetica"]; subgraph cluster_a{label="a" fontname="Helvetica"; a1->a2[label="a"]; a2[shape=doublecircle];} subgraph cluster_u{label="r1 + r2" fontname="Helvetica"; u0; u1[shape=box label="r1"]; u2[shape=box label="r2"]; uf[shape=doublecircle]; u0->u1[label="λ"]; u0->u2[label="λ"]; u1->uf[label="λ"]; u2->uf[label="λ"];} subgraph cluster_c{label="r1 r2" fontname="Helvetica"; c1[shape=box label="r1"]; c2[shape=box label="r2"]; c1->c2[label="λ"];} subgraph cluster_s{label="r*" fontname="Helvetica"; s0; s1[shape=box label="r"]; sf[shape=doublecircle]; s0->s1[label="λ"]; s1->sf[label="λ"]; s0->sf[label="λ"]; sf->s0[label="λ"];} }
  • or: a new start state with λ-arrows into both machines — “guess which one”.
  • then: a λ-arrow from the end of the first machine to the start of the second.
  • repeat: a way to skip straight to the end (zero times) and a λ-arrow back to go again.

In the other direction, you can take any automaton and remove its states one by one, writing the paths through each removed state as small regexes on the arrows, until one arrow with the whole regex remains. You don’t need to be fast at that — you need to know that it works, because that’s what makes the theorem true.

3.5 Back in the real world PL

Why should a programmer care? Because the very first thing an interpreter does with your code is chop it into “words” — numbers, names, operators — and each kind of word is described by a regular expression:

TokenPatternIn course notation
integer[0-9]+\(dd^*\) with \(d=0+1+\dots+9\)
identifier[a-zA-Z_][a-zA-Z0-9_]*letter, then (letter + digit)\(^*\)
optional sign-?\(\lambda + -\)

The part of an interpreter that does this — the lexer — is literally a finite automaton built from those patterns. You’ll see it at work in Chapter 22.
